# 05 — Worker Protocol

> **Document purpose:** Defines the complete language-independent HTTP protocol between Orqen and customer workers — every operation, request/response shape, headers, error codes, and connection behavior.  
> **Read before:** Implementing any SDK, any worker-facing API handler, or the long-poll subsystem.  
> **Reference when:** Adding a new protocol operation, debugging worker connectivity, or implementing a new language SDK.

---

## Design Principles

1. **Language-independent** — the protocol is plain HTTP/JSON. Any language with an HTTP client can implement a worker.
2. **Worker-initiated** — workers always initiate connections. The server never pushes to workers directly.
3. **Stateless server-side per request** — each HTTP request is self-contained. Worker state (registration, concurrency) is stored in PostgreSQL, not in connection memory.
4. **Long polling for job delivery** — the server holds the poll connection open until a job is available. No WebSocket, no SSE, no gRPC in V1.
5. **Explicit acknowledgement** — a worker must acknowledge receipt of a job before it begins execution. This separates delivery from execution.

---

## Authentication

Every worker request must include the project API key in the `Authorization` header:

```
Authorization: Bearer orqen_live_xxxxxxxxxxxxxxxxxx
```

The server resolves the project from the key. Requests without a valid key return `401 Unauthorized`. There is no separate worker token — workers authenticate as the project.

---

## Base URL

```
https://<orqen-host>/api/v1
```

All worker protocol endpoints are under `/api/v1/worker/`.

---

## Protocol Operations Overview

| Operation | Method | Path | Description |
|---|---|---|---|
| Register Worker | `POST` | `/worker/register` | Declare worker existence, capabilities, concurrency |
| Heartbeat | `POST` | `/worker/heartbeat` | Signal worker is still alive |
| Poll for Job | `GET` | `/worker/poll` | Long-poll — holds until a job is available |
| Acknowledge Job | `POST` | `/worker/jobs/:job_id/ack` | Confirm job received, about to execute |
| Submit Success | `POST` | `/worker/jobs/:job_id/result` | Return successful execution result |
| Submit Failure | `POST` | `/worker/jobs/:job_id/failure` | Return execution error |
| Graceful Shutdown | `POST` | `/worker/shutdown` | Signal worker is shutting down cleanly |

## 1. Register Worker

Registers the worker with Orqen. Must be called once before polling. Re-registration with the same worker ID updates the worker's record.

### Request

```
POST /api/v1/worker/register
Authorization: Bearer orqen_live_xxx
Content-Type: application/json
```

```json
{
    "worker_id": "worker_7j3nbf2a",
    "capabilities": ["send_email", "generate_pdf", "resize_image"],
    "concurrency": 10
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `worker_id` | `string` | YES | Unique identifier for this worker instance. Generated by the SDK. |
| `capabilities` | `string[]` | YES | List of job types this worker can handle. Must be non-empty. |
| `concurrency` | `integer` | YES | Maximum number of jobs this worker can run in parallel. Min: 1. |

### Response — `200 OK`

```json
{
    "worker_id": "worker_7j3nbf2a",
    "project_id": "proj_abc123",
    "registered_at": "2026-09-27T10:00:00Z"
}
```

### Response — `400 Bad Request`
```json
{
    "error": "INVALID_REQUEST",
    "message": "capabilities must not be empty"
}
```

### Behavior
- If `worker_id` does not exist: creates a new worker record in PostgreSQL and registers it in all relevant CRS instances.
- If `worker_id` already exists (reconnect case): updates `last_heartbeat_at`, resets status to `IDLE`, and re-registers in CRS.
- A worker is associated with the project of the authenticating API key. The `worker_id` must be unique within a project.

---

## 2. Heartbeat

Signals that the worker is still alive. Must be sent periodically while the worker is running.

### Request

```
POST /api/v1/worker/heartbeat
Authorization: Bearer orqen_live_xxx
Content-Type: application/json
```

```json
{
    "worker_id": "worker_7j3nbf2a"
}
```

### Response — `200 OK`

```json
{
    "status": "ok"
}
```

### Response — `404 Not Found`
```json
{
    "error": "WORKER_NOT_FOUND",
    "message": "worker_id does not exist in this project"
}
```

### Heartbeat Timing
- Workers must send a heartbeat every **15 seconds** by default.
- The server marks a worker `OFFLINE` if no heartbeat is received within **45 seconds** (3x the interval).
- These values should be configurable via server environment variables.

### Behavior
- Updates `last_heartbeat_at` on the worker record.
- If the worker was previously `OFFLINE` but sent a heartbeat, it is treated as a reconnect — status is reset to `IDLE` and it is re-registered in CRS.

## 3. Poll for Job

The core long-polling endpoint. The worker calls this to receive its next job. The connection is held open by the server until a job is available for this worker, or until the timeout is reached.

### Request

```
GET /api/v1/worker/poll?worker_id=worker_7j3nbf2a&timeout=30
Authorization: Bearer orqen_live_xxx
```

| Query Param | Type | Required | Description |
|---|---|---|---|
| `worker_id` | `string` | YES | The polling worker's ID |
| `timeout` | `integer` | NO | Max seconds to hold the connection. Default: 30. Max: 60. |

### Response — `200 OK` (job available)

```json
{
    "job_id": "job_4p8ycw6m",
    "attempt_id": "attempt_2x5hqe9r",
    "attempt_num": 1,
    "job_type": "generate_pdf",
    "payload": {
        "document_id": "doc_xyz",
        "format": "A4"
    },
    "priority": 5,
    "timeout_seconds": 120,
    "created_at": "2026-09-27T10:01:00Z"
}
```

| Field | Type | Description |
|---|---|---|
| `job_id` | `string` | The job identifier |
| `attempt_id` | `string` | The unique ID of this specific attempt |
| `attempt_num` | `integer` | Which attempt number this is (1 = first try) |
| `job_type` | `string` | The capability the worker should invoke |
| `payload` | `object` | Input data for the worker function |
| `priority` | `integer` | Job priority (informational) |
| `timeout_seconds` | `integer` | How long the worker has to complete this attempt |
| `created_at` | `string` | When the job was originally enqueued |

### Response — `204 No Content` (timeout, no job available)

The connection was held for the full timeout period and no job became available. The worker should immediately re-poll.

```
HTTP/1.1 204 No Content
```

### Response — `409 Conflict` (worker at capacity)
```json
{
    "error": "WORKER_AT_CAPACITY",
    "message": "worker has reached its concurrency limit"
}
```

### Response — `404 Not Found` (worker not registered)
```json
{
    "error": "WORKER_NOT_FOUND",
    "message": "worker_id does not exist — call /worker/register first"
}
```

### Long-Poll Mechanics
```
Worker calls GET /worker/poll
        │
        ▼
Server checks if a READY job exists for this worker's capabilities
        │
  ┌─────┴──────┐
  │            │
Job exists   No job
  │            │
  ▼            ▼
Return job   Hold connection open (up to timeout seconds)
immediately       │
              Job arrives?
              │         │
             YES        NO (timeout)
              │         │
           Return job  Return 204
```

### Server-Side Behavior on Job Dispatch
When a job is dispatched via poll response:
1. Job status → `RUNNING`
2. `job.worker_id` set to this worker
3. New `job_attempts` row created (`status: RUNNING`, `attempt_num` incremented)
4. `worker.current_job_count` incremented
5. If worker is now at concurrency limit: `sched.Exclude(workerID)` on all capability CRS instances

## 4. Acknowledge Job

Sent immediately after the worker receives a job from the poll response, before beginning execution. Confirms safe delivery.

### Request

```
POST /api/v1/worker/jobs/:job_id/ack
Authorization: Bearer orqen_live_xxx
Content-Type: application/json
```

```json
{
    "worker_id": "worker_7j3nbf2a",
    "attempt_id": "attempt_2x5hqe9r"
}
```

### Response — `200 OK`

```json
{
    "status": "acknowledged"
}
```

### Response — `409 Conflict`
```json
{
    "error": "ATTEMPT_MISMATCH",
    "message": "attempt_id does not match current attempt for this job"
}
```

### Behavior
- Updates `job_attempts.status` for the given `attempt_id` to confirm delivery.
- If `attempt_id` does not match the current active attempt (e.g. a previous attempt's ACK arriving late), return `409` and ignore.

---

## 5. Submit Success

Sent when the worker has successfully executed the job function and has a result to return.

### Request

```
POST /api/v1/worker/jobs/:job_id/result
Authorization: Bearer orqen_live_xxx
Content-Type: application/json
```

```json
{
    "worker_id": "worker_7j3nbf2a",
    "attempt_id": "attempt_2x5hqe9r",
    "result": {
        "pdf_url": "https://storage.example.com/doc_xyz.pdf",
        "pages": 4
    }
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `worker_id` | `string` | YES | The worker submitting the result |
| `attempt_id` | `string` | YES | The attempt ID received in the poll response |
| `result` | `object` | NO | Arbitrary JSON result payload. May be null. |

### Response — `200 OK`

```json
{
    "job_id": "job_4p8ycw6m",
    "status": "COMPLETED"
}
```

### Response — `409 Conflict` (stale attempt)
```json
{
    "error": "ATTEMPT_MISMATCH",
    "message": "result submitted for a superseded attempt — ignored"
}
```

### Server-Side Behavior on Success
1. Validate `attempt_id` matches current active attempt — if not, return `409` and stop
2. `job_attempts` row: `status → SUCCESS`, `completed_at` set, `result` stored
3. `jobs` row: `status → COMPLETED`, `result` stored, `completed_at` set, `worker_id` cleared
4. `worker.current_job_count` decremented
5. If worker was excluded from CRS due to capacity: `sched.Include(workerID)` on all capability instances
6. DAG engine: check if any downstream jobs were waiting on this job → transition them to `READY` if all deps satisfied

---

## 6. Submit Failure

Sent when the worker's function threw an error or the job could not be completed.

### Request

```
POST /api/v1/worker/jobs/:job_id/failure
Authorization: Bearer orqen_live_xxx
Content-Type: application/json
```

```json
{
    "worker_id": "worker_7j3nbf2a",
    "attempt_id": "attempt_2x5hqe9r",
    "error": "PDF rendering service timed out after 30s",
    "error_code": "RENDER_TIMEOUT"
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `worker_id` | `string` | YES | The worker submitting the failure |
| `attempt_id` | `string` | YES | The attempt ID received in the poll response |
| `error` | `string` | YES | Human-readable error message |
| `error_code` | `string` | NO | Optional machine-readable error code |

### Response — `200 OK` (will retry)

```json
{
    "job_id": "job_4p8ycw6m",
    "status": "RETRYING",
    "next_attempt_at": "2026-09-27T10:03:05Z",
    "attempts_remaining": 2
}
```

### Response — `200 OK` (retries exhausted)

```json
{
    "job_id": "job_4p8ycw6m",
    "status": "FAILED",
    "attempts_remaining": 0
}
```

### Server-Side Behavior on Failure
1. Validate `attempt_id` matches current active attempt — if not, ignore
2. `job_attempts` row: `status → FAILED`, `completed_at` set, `error` stored
3. `worker.current_job_count` decremented; `sched.Include` if was excluded
4. If `attempt_count < max_retries`:
   - `jobs.status → RETRYING`
   - Schedule re-queue after backoff duration
   - On backoff expiry: `jobs.status → QUEUED` → enters normal scheduling pipeline
5. If `attempt_count >= max_retries`:
   - `jobs.status → FAILED`
   - `jobs.error` set to the final error message
   - DAG engine: propagate failure to downstream jobs per failure policy

---

## 7. Graceful Shutdown

Sent when the worker is shutting down cleanly. Allows the server to stop assigning new jobs to this worker.

### Request

```
POST /api/v1/worker/shutdown
Authorization: Bearer orqen_live_xxx
Content-Type: application/json
```

```json
{
    "worker_id": "worker_7j3nbf2a"
}
```

### Response — `200 OK`

```json
{
    "status": "ok",
    "message": "worker marked for shutdown — no new jobs will be assigned"
}
```

### Behavior
- Worker is immediately excluded from all CRS capability pools: `sched.Exclude(workerID)` for all capabilities
- Worker status set to `OFFLINE`
- Any in-flight jobs the worker is currently executing are allowed to complete — the worker continues sending heartbeats and submitting results for those jobs
- Once all in-flight jobs are completed, the worker can safely terminate

### Graceful Shutdown vs Crash
| Scenario | Detection | In-flight Jobs |
|---|---|---|
| Graceful shutdown | Explicit `/worker/shutdown` call | Allowed to complete normally |
| Worker crash | Heartbeat timeout (45s) | Recovered and requeued by reliability layer |

## Connection Lifecycle

The full lifecycle of a worker from startup to shutdown:

```
Worker starts
      │
      ▼
POST /worker/register
      │
      ▼
Loop:
  ├── POST /worker/heartbeat  (every 15s, in background)
  │
  └── GET /worker/poll  ──────────────────────────────────┐
            │                                             │
        Job received                                 204 (timeout)
            │                                             │
            ▼                                             │
    POST /worker/jobs/:id/ack                             │
            │                                             │
            ▼                                             │
    Execute customer function                             │
            │                                             │
     ┌──────┴──────┐                                      │
     │             │                                      │
   Success      Failure                                   │
     │             │                                      │
     ▼             ▼                                      │
POST /result  POST /failure                               │
     │             │                                      │
     └──────┬───────┘                                     │
            │                                             │
            └─────────────────────────────────────────────┘
                        (re-poll immediately)

Worker shutdown signal received:
      │
      ▼
POST /worker/shutdown
      │
      ▼
Complete any in-flight jobs
      │
      ▼
Worker process exits
```

## Error Response Format

All error responses follow this structure:

```json
{
    "error": "ERROR_CODE",
    "message": "Human-readable description of what went wrong"
}
```

### Standard Error Codes

| Code | HTTP Status | Meaning |
|---|---|---|
| `UNAUTHORIZED` | `401` | Missing or invalid API key |
| `WORKER_NOT_FOUND` | `404` | worker_id not registered in this project |
| `JOB_NOT_FOUND` | `404` | job_id not found in this project |
| `WORKER_AT_CAPACITY` | `409` | Worker has reached its concurrency limit |
| `ATTEMPT_MISMATCH` | `409` | Submitted attempt_id does not match current active attempt |
| `INVALID_REQUEST` | `400` | Request body is malformed or missing required fields |
| `WORKER_OFFLINE` | `409` | Operation rejected because worker is marked OFFLINE |
| `INTERNAL_ERROR` | `500` | Unexpected server error |

## Timeout Handling

### Poll Timeout
- Default: 30 seconds
- Maximum: 60 seconds
- On timeout: server returns `204 No Content`; worker immediately re-polls

### Job Execution Timeout
- Defined per job via `timeout_seconds`
- Server tracks `started_at` on the attempt
- If the worker does not submit a result within `timeout_seconds`, the server treats it as a failure
- The reliability layer's heartbeat monitor detects this and recovers the job

### Heartbeat Timeout
- Worker must heartbeat every 15 seconds
- Server marks worker `OFFLINE` after 45 seconds of silence
- All `RUNNING` jobs assigned to that worker are recovered and requeued

## SDK Implementation Requirements

When implementing a new language SDK, it must:

1. Generate a stable `worker_id` on first run and persist it (e.g. to a local file or config) so reconnects reuse the same ID
2. Call `POST /worker/register` on startup
3. Run a background heartbeat loop every 15 seconds
4. Run a polling loop: call `GET /worker/poll`, handle `200` (execute job) and `204` (re-poll)
5. After receiving a job: call `POST /worker/jobs/:id/ack` before invoking the customer function
6. After function completes: call `POST /worker/jobs/:id/result` or `POST /worker/jobs/:id/failure`
7. Immediately re-poll after submitting a result or failure
8. On process shutdown signal: call `POST /worker/shutdown`, wait for in-flight jobs to complete, then exit
9. Handle network errors with exponential backoff before retrying the failed request
10. Never call `result` or `failure` with a stale `attempt_id` — always use the `attempt_id` received in the most recent poll response
